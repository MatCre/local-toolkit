Local Toolkit Architecture

How the six tools fit together, what happens when a prompt leaves your code, and where each session adds a layer. Updated at the end of every session.

01 · The big picture

One AI layer, five tools on top

Every tool talks to IChatClient, an interface from Microsoft.Extensions.AI. None of them knows whether Claude, OpenAI or Ollama answers. That's what lets a tool keep working with Wi-Fi off or once the monthly budget runs out.

Toolkit.AI

Project 1 · Sessions 1–3 Provider routing, budget cap, caching, fallback to local. Exposes services.AddToolkitAI(config).

Toolkit.Vault

02 · The request pipeline

What happens to a prompt

The AI layer is a chain of clients, each wrapping the next, like ASP.NET Core middleware. A layer can inspect the request, change it, answer it without calling further in (a cache hit), or pass it inward and act on the response coming back. You build the chain in one place, ServiceCollectionExtensions.cs, with AddChatClient(inner).UseXxx().

BuiltRuns on your machinePlanned
Your code: Sandbox / Vault / Cards …caller Asks DI for IChatClient and calls GetResponseAsync(prompt), or GetStreamingResponseAsync to receive tokens as they arrive.
LoggingChatClientSession 1 From .UseLogging(). At Debug it writes "invoked" and "completed". At Trace, which Sandbox uses, it also writes the full prompt, the full response, token usage and Ollama's timings. Serilog sends these entries to the console and to a log file.
ToolkitCachingChatClientSession 3 Microsoft.Extensions.AI's DistributedCachingChatClient with two additions. The key is built from normalized text: lower case, single spaces, no trailing . ? !, so "What is SQLite?" and "what is sqlite" share an entry; the model still receives the original text. And an answer served from the cache is marked toolkit.cacheHit, so callers can tell. On a hit, nothing further in runs. Storage is our SqliteDistributedCache in data/response-cache.db, kept for 7 days, so it survives restarts. Turn it off with ToolkitAI:Cache:Enabled=false.
VaultCaptureChatClientSession 5 Saves each question and answer into the vault, tagged #ai-capture with the provider and model. It sits inside the cache, so a cache hit is never saved twice. It's added from outside through the IToolkitChatLayer extension point, so Toolkit.AI has no reference to the vault. A request marked WithoutVaultCapture(), a failed call, or text that looks like a secret is never saved.
BudgetChatClientSession 3 Totals this month's estimated cost from the call log (calendar month, your time zone). At or over MonthlyCapUsd, it adds a toolkit.localOnly hint to the request's options, and the router then tries local providers only. If spending can't be read, it plays safe and goes local. Left out when no cap is set.
ToolkitRoutingChatClientSession 2 Tries providers in ProviderOrder. Each attempt gets its own timeout. Any failure other than the caller cancelling (an error, a rate limit, a timeout) moves on to the next provider. Every attempt becomes a row in the SQLite call log, and the answer is tagged with the provider that gave it.
first try ↓ · on failure → next
OpenAIClient (openrouter)1st The official OpenAI SDK pointed at https://openrouter.ai/api/v1, model openrouter/free. SDK retries are off, so a 429 falls back right away. Skipped until an API key is set.
internet · HTTPS POST /chat/completions
OpenRouter → a free modelcloud The free router picks a model. 20 requests a minute and 50 a day. Some free providers may train on prompts.
OllamaApiClient (ollama)2nd OllamaSharp with its HttpClient timeout off, so the router's 120 s limit covers a cold model load.
process boundary · HTTP POST localhost:11434/api/chat
Ollama server → qwen2.5-coder:7blocal Loads the model into GPU memory on first use and keeps it there about 5 minutes after the last call.

How layers talk to each other: the budget layer can't reach into the router. It can only change what it passes inward. So it puts a hint in ChatOptions.AdditionalProperties, the router reads it, and the router removes it before the request reaches a provider. Some clients send unknown properties to the server as extra request fields, which is why the hint is removed.

Why this order? Logging sits outermost so it sees every call, including cache hits. The cache sits outside the budget check so a cached answer costs nothing and isn't counted. The router is innermost of the custom layers because it's the one that picks a vendor.

03 · Startup sequence

From dotnet run to the first token

  1. SDK selection. The dotnet muxer reads global.json, which asks for 11.0.100, and finds that SDK. The dotnetup install has it; C:\Program Files\dotnet doesn't (see the PATH note below).
  2. Build. MSBuild applies Directory.Build.props (net11.0, nullable, warnings as errors) and Directory.Packages.props (one version per NuGet package) to every project, then compiles Toolkit.AI and Sandbox.
  3. Host builder. Host.CreateApplicationBuilder sets up configuration, logging and a DI container: the same plumbing ASP.NET Core and Worker Services use.
  4. Configuration loads in layers. The table below shows the order. Later sources override earlier ones key by key.
  5. Registration. AddToolkitAI(config) binds the ToolkitAI section to ToolkitAIOptions, registers validation, and registers a factory for the IChatClient pipeline. Nothing is constructed yet.
  6. Build the container. builder.Build() freezes the registrations.
  7. Resolve. GetRequiredService<IChatClient>() runs the factory: it reads the options, which triggers validation. ChatProviderFactory builds one client per provider and skips any cloud provider with no API key, logging a warning. It wraps them in ToolkitRoutingChatClient, then in LoggingChatClient.
  8. Call. await chat.GetResponseAsync(prompt) waits for the whole reply. The ChatResponse it returns holds the text, the model ID and Usage token counts. The streaming version, GetStreamingResponseAsync, shows tokens sooner, but Trace logging then writes one entry per chunk, so Sandbox doesn't use it.
04 · Configuration

Where settings come from

OrderSourceIn Git?Use it for
1appsettings.jsonYesProvider order, endpoints, models, timeouts, log levels
2appsettings.{Environment}.jsonYesPer environment (Development, Production)
3appsettings.Local.jsonNo (ignored)Paths and settings specific to this machine
4dotnet user-secretsNoThe OpenRouter key: ToolkitAI:Providers:openrouter:ApiKey. The host normally loads these only in Development; Sandbox loads them explicitly, so they're always read.
5Environment variablesNoToolkitAI__Providers__ollama__Model=llama3.2:3b

Providers are a dictionary keyed by name, not a JSON array. That gives each setting a stable address that a secret or environment variable can override, such as ToolkitAI:Providers:openrouter:ApiKey. In an array it would be Providers:0:ApiKey, which breaks as soon as the order changes. The ToolkitAI:Providers:ollama:Model key in JSON, ToolkitAI__Providers__ollama__Model as an environment variable, and the Model property on ProviderOptions are the same setting. The binder maps one to the other by name.

05 · Logging

Where the logs go

Code logs through ILogger<T> from Microsoft.Extensions.Logging. AddSerilog in Program.cs swaps in Serilog to write those entries out. The Serilog section of appsettings.json sets levels and destinations, so changing either needs no code.

DestinationFormatWhere
ConsoleColoured, [09:45:13 VRB] Source headerThe terminal running the app
Rolling fileFull date, time and UTC offsetlogs/sandbox-YYYYMMDD.log under the folder you ran from (repo root for dotnet run). A new file each day; the last 14 are kept. Git ignores the folder.

Levels: Default: Warning keeps the framework quiet, and an override sets Microsoft.Extensions.AI to Verbose, Serilog's name for Trace. To read only the model calls later, open the log file or follow it with Get-Content logs\sandbox-*.log -Wait.

Later: OpenTelemetry and the Aspire dashboard. Logs are text. Traces add structure: a .UseOpenTelemetry() layer in the pipeline would record each call as a span with model, tokens and duration as fields, and the Aspire dashboard would show them as a clickable timeline. Planned for when routing makes "which provider answered, and how fast" worth seeing. It needs Docker for the dashboard.

At Trace, Ollama reports its own timing. One warm call took 0.41s inside Ollama, but 2.7s end to end; the rest is the app starting up: the host, JIT compilation and the first HTTP connection. Cold starts are what a local fallback costs, so the router gives Ollama a 120 s timeout.

Session 2: a fallback, in the call log

The Sandbox ran with OpenRouter's address set to a host that doesn't exist, which is how it looks with Wi-Fi off. The caller got an answer and saw one warning line. data/toolkit-ai.db recorded both attempts:

ProviderModelTokens in / outDurationCostResult
openrouteropenrouter/free–83 ms–Failed: No such host is known

Your own Wi-Fi-off run, against the real openrouter.ai, logged the same pattern: a failed openrouter row ("No such host is known", 88 ms), then ollama answering in 4.2 s. That passed Session 2's done-when check.

A failed attempt costs very little when the network is down: the DNS lookup fails within milliseconds. The slow case is a cloud provider that accepts the connection and then hangs, which the 30 s OpenRouter timeout covers. Free-tier limits are part of the design: at 20 requests a minute and 50 a day, a 429 is an expected event, not an error. Some free providers may train on prompts, so private data, such as the bank transactions in Session 8, should go straight to Ollama.

A cache hit doesn't count against the 50 free requests a day. A cached answer carries the provider name and token counts of the call that first produced it, so at first a hit looked exactly like a fresh openrouter call. Now the caching layer marks hits, and the Sandbox prints [0.2s, from cache, no provider called; first answered by openrouter -> …]. The budget cap can't be shown on free models, where every cost is $0, so a unit test proves it: with $5 spent and a $1 cap, the request goes to the local model and the cloud fake is never called.

08 · Answer vault

How the vault stores and finds things

The vault is a SQLite file with two parts: a normal entries table holding your text, and an FTS5 full-text index over it. The index works like a book's index: for each word, it lists the entries containing it, so a search never reads every entry. Triggers keep the two in step automatically.

vault add / search / show / list / removeToolkit.Vault.Cli System.CommandLine parses the command line, generates --help and reports bad input. Text for add comes only from where you say: --file, --clipboard (via TextCopy), or piped input.
IVaultStoreToolkit.Vault The contract the CLI uses: add, get, list, search, remove. SearchText splits typed text into words the same way for every database.
SqliteVaultStore + FtsQueryToolkit.Vault.Sqlite The SQLite implementation, using Dapper. FtsQuery turns the words into a safe FTS5 query, so punctuation and words like NOT can never break it.
entriestable id, title, body, source, tags, created_utc. The source of truth.
entries_ftsFTS5 index Indexes title, body and tags with the porter unicode61 tokenizer. Stores no text of its own; insert, update and delete triggers keep it current.

What a search does

You typeSent to FTS5Why
retry polly("retry" OR "retry"*) AND ("polly" OR "polly"*)Every word must match. Quoting makes each one a plain word.
retryfinds "retries", "retrying"The porter stemmer reduces words to a common root.
sqlifinds "SQLite"The * form matches half-typed words.
C# foo-bar NOT"C", "foo", "bar", "NOT"Punctuation separates words; operators become plain words.

Results are ranked by BM25, a standard relevance score that favours rare words and short fields. A match in the title counts 10× a body match, and a tag match 5×. The excerpt under each result comes from FTS5's snippet(), with matched words in yellow.

A bug the tests caught: the first version joined the bracketed groups with spaces. FTS5 accepts spaces as AND between plain words, but not between brackets, so every multi-word search failed with a syntax error. The punctuation tests failed before it ever reached you; the fix was an explicit AND.

Keeping secrets out

Entries are plain text and appear in search results, so the vault refuses anything that looks like a credential. The first version read the clipboard whenever no other source was given. A stale clipboard holding an API key was saved as a "Retry with Polly" entry and then printed by the next search. Three changes followed:

ChangeWhereWhat it prevents
The clipboard is read only with --clipboardCLISaving whatever happened to be copied
Every add prints a preview of the stored textCLIA wrong paste going unnoticed until the next search
SecretScanner refuses likely secrets unless --allow-secret is givenVault core: NewVaultEntry.Validate(), called by every storeKeys stored by any route, including Session 5's automatic capture

The scanner looks for two things. Known formats: providers deliberately prefix their keys (sk-, ghp_, AKIA, AIza, xox…) so leaks can be spotted; it also catches private key blocks, JWTs and passwords in connection strings. Random-looking tokens: 32 or more unbroken letters and digits with high Shannon entropy, a measure of how unpredictable each character is. Generated keys score about 5 bits per character, English about 3, and hex hashes at most 4, so git hashes pass. Errors only ever show a masked form, like sk-or-v…3d4. It's a safety net, not a guarantee.

08b · The data layer

Ports and adapters: swapping databases later

The toolkit's core code never talks to a database directly. It talks to small interfaces, the ports. Each database gets its own adapter project that implements them. Today every adapter is SQLite; moving to EF Core, SQL Server or Postgres means adding an adapter, not changing the core or the apps.

Port (in the core)Used bySQLite adapter todayA SQL Server adapter would use
IVaultStorevault CLI; later the Blazor page and auto-captureSqliteVaultStore: FTS5EF Core or Dapper, plus SQL Server full-text search (CONTAINS, FORMSOF)
IAiCallLogrouter (writes), budget (reads)SqliteAiCallLogEF Core: one table, a SUM query
IDistributedCache (.NET's own)response cacheSqliteDistributedCacheMicrosoft's ready-made Microsoft.Extensions.Caching.SqlServer

Project references point inward, toward the core: Toolkit.AI.Sqlite → Toolkit.AI and Toolkit.Vault.Sqlite → Toolkit.Vault. The core projects reference no database package at all, so they can't accidentally start depending on SQLite.

One line picks the database. Each app has a composition root, the place where it builds its objects:

// Sandbox: Program.cs
builder.Services.AddToolkitAI(config)
                .AddToolkitAISqlite();          // ← storage adapter

// vault CLI: Program.cs
IVaultStore Store(...) => new SqliteVaultStore(path);   // ← storage adapter

If no adapter is registered, AddToolkitAI stops at startup with a message saying what to add. It doesn't quietly log nothing, because the budget cap reads its spending from the call log.

Contract tests keep adapters honest. VaultStoreContractTests and AiCallLogContractTests are abstract classes holding the behaviour every implementation must have: every word must match, other forms of a word match, half-typed words match, best match first, and spending is totalled across time zones. Each adapter has a small subclass that runs them; the in-memory call log used in tests runs them too.

Moving the vault to SQL Server later

  1. Create Toolkit.Vault.SqlServer with a SqlServerVaultStore : IVaultStore, using EF Core or Dapper.
  2. Set up a full-text catalog and index on the entries table. Build the CONTAINS query from SearchText.Words(text), for example FORMSOF(INFLECTIONAL, "retry") OR "retry*" for each word.
  3. Add SqlServerVaultStoreTests : VaultStoreContractTests, pointing at a test database, and make it pass. Ranking and snippets need SQL Server's own functions, since it has nothing like FTS5's snippet().
  4. Change the one line in the CLI's Program.cs, and write a one-off copy script to move existing entries across.

Schema migrations. Session 5 added an external_id column to a vault you were already using. Every SQLite store now passes an ordered list of migrations to SqliteDatabase. SQLite keeps a counter in each file, PRAGMA user_version; on open, the migrations the file hasn't had yet run in order, each in a transaction with its counter bump. A Session 4 vault (version 0, tables already there) is upgraded in place, and a test checks exactly that. Rule: never edit a migration that has shipped; add a new one. EF Core migrations work the same way, with generated C# instead of SQL.

Why not switch to EF Core now? EF Core makes swapping databases easy for plain tables, but it doesn't hide full-text search: each database has its own, and EF Core would need raw SQL for it either way. Dapper keeps the SQL visible while you learn. The interfaces mean EF Core can come later, one adapter at a time.

PATH note: two dotnet installs

C:\Program Files\dotnet (SDKs 8 and 10) comes before the dotnetup install (which also has 11.0.100) on PATH, so a plain dotnet picks the old one and fails in this repo with an SDK-not-found error. To fix it, move %LOCALAPPDATA%\dotnetup\dotnet above C:\Program Files\dotnet in your user PATH, or point your IDE's .NET path at the dotnetup folder.

09 · Glossary

Terms used in the code

IChatClient
The vendor-neutral chat interface in Microsoft.Extensions.AI. It has two methods, one for a whole response and one for a stream.
ChatClientBuilder
What AddChatClient returns. Each .UseXxx() adds a wrapping layer, and the last one added becomes the outermost.
DelegatingChatClient
The base class for writing your own layer (Router, Budget, VaultLogging). You override the two methods and call base to pass the request inward.
GetService<T>()
Walks down the pipeline to find a layer of type T. The tests use it to confirm Ollama is innermost.
Options pattern
Binds a config section to a class (IOptions<ToolkitAIOptions>). ValidateOnStart makes bad config fail when the app starts instead of on first use.
Central Package Management
Directory.Packages.props holds every package version. A .csproj lists package names only.
ToolkitRoutingChatClient
Our router. Microsoft.Extensions.AI 11 also ships an abstract RoutingChatClient and a FailoverChatClient template that do similar work. We wrote our own to learn how it works, and could move onto theirs later.
AllProvidersFailedException
What the router throws when every provider fails. InnerExceptions holds one exception per provider, in order.
Dapper
Adds ExecuteAsync and QueryAsync to a database connection. You write the SQL; it fills @Name parameters from an object's properties and turns results into C# objects. The call log uses it now, and the vault will in Session 4. EF Core, the full ORM alternative, would also generate the SQL and manage the tables, which is more than this needs.
IDistributedCache
.NET's standard interface for a byte store with expiry: Get, Set, Refresh and Remove. The AI caching layer only knows this interface, so the store behind it could be memory, SQLite or Redis. Ours is registered under its own DI key, so it can't clash with a cache the app uses for something else.
Cache key normalization
Changing the text used to build the key, never the text sent to the model. It costs a little precision: case and indentation in code drop out of the key. Turn it off with ToolkitAI:Cache:NormalizeKeys=false. A version marker in every key keeps normalized and plain keys from matching each other.
IToolkitChatLayer
The AI layer's extension point. Another package registers one in DI, and AddToolkitAI places it between the cache and the budget check. Vault capture uses it, so the AI core never references the vault.
Schema migration
A numbered change to a database's structure, applied once per database file, in order. Here SQLite's PRAGMA user_version records how many have run.
Static server rendering
Blazor's simplest mode: components render to HTML on the server per request, with no live connection and no WebAssembly. Forms and links work like a classic website.
Shannon entropy
The average information per character in a piece of text, in bits. Random keys are high, words are low. The secret scanner uses it to tell generated tokens from ordinary long words.
Ports and adapters
Also called hexagonal architecture. The core defines interfaces for what it needs from the outside world (ports); separate projects implement them for a particular technology (adapters). Swapping technology means swapping adapters.
Composition root
The one place in an app where objects are built and joined together, usually Program.cs. It's the only code that names concrete classes such as SqliteVaultStore; everything else uses the interfaces.
Contract tests
Tests written once against an interface, in an abstract class, and run against every implementation through a subclass. They define what "works" means for any adapter.
FTS5
SQLite's built-in full-text search. A virtual table that behaves like a table but is an index underneath. Query it with MATCH, rank results with bm25() and cut excerpts with snippet().
External-content FTS table
An FTS5 index that reads its text from another table (content='entries') instead of keeping a copy. It's smaller, but you must keep it in step with that table, which the triggers do.
Stemming
Reducing words to a root before indexing and searching, so "retries", "retrying" and "retry" all match. The porter tokenizer does this for English.
System.CommandLine
Microsoft's command-line parser. You declare commands, arguments and options as objects, and it handles parsing, --help, errors and exit codes.
Fail closed
When a safety check can't get its answer, take the safe option. The budget layer goes local-only if it can't read the call log.
FakeTimeProvider
A clock tests can set and move forward. It's how the tests check month boundaries and cache expiry without waiting. Production code takes a TimeProvider instead of reading DateTime.Now for this reason.
User secrets
A JSON file in your user profile (%APPDATA%\Microsoft\UserSecrets\local-toolkit-sandbox\), outside the repo. It's merged into configuration like any other source.
Serilog
A logging library that sits behind ILogger. Sinks are its destinations (console, file, later Seq or OpenTelemetry). Output templates set the line format.
Generic Host
Host.CreateApplicationBuilder: configuration, logging and DI in one object. Workers (S9) and Blazor apps (S5, S13) use the same model.
